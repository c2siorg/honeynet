# Contributing

Thanks for contributing to Honeynet.

The current validated implementation centers on multi-region Cowrie deployment with centralized telemetry and analysis, but the project is intended to grow into a broader honeypot deployment framework. Good contributions usually improve one of these areas:

- infrastructure modules
- honeypot automation
- telemetry and enrichment
- analytics and documentation

## Workflow

1. Fork the repository.
2. Create a focused feature branch.
3. Keep changes scoped to a single problem when possible.
4. Validate the affected workflow locally or in a sandbox account.
5. Open a pull request with a clear summary, validation notes, and screenshots or logs when useful.

## Branch and Commit Style

Prefer short, descriptive commit messages such as:

- `feat(honeypot): add reusable multi-region Terraform module`
- `feat(telemetry): handle gzip-compressed Fluent Bit uploads`
- `docs(architecture): update end-to-end telemetry flow`

## Pull Request Expectations

A strong PR should include:

- what problem it solves
- how it relates to existing work
- what changed at a high level
- how it was validated

If your work builds on another open PR, say that clearly in the description.

## Validation Guidance

For infrastructure or telemetry changes, try to validate as much of the real workflow as possible.

Examples:

- Terraform plan/apply succeeds in a sandbox account
- Cowrie is reachable on port `2222`
- raw logs arrive in S3
- Lambda enrichment succeeds
- Glue crawler discovers the enriched schema
- Athena queries return expected fields

For documentation-only PRs, confirm that commands, file paths, and architecture descriptions match the current repository layout.

## Repository Notes

- `ansible/inventory.ini` is generated during deployment.
- `terraform/modules/telemetry/lambda_enrichment.zip` is generated by Terraform and should not be committed.
- secrets should not be committed; keep them in ignored tfvars files or environment variables

## Good Follow-Up Areas

Useful contribution areas include:

- support for additional honeypots
- schema normalization across honeypot types
- analyst query packs for Athena
- architecture and deployment documentation
- reliability improvements in deployment and forwarding

## Questions and Collaboration

If you are building on top of another contributor’s work, prefer additive follow-up PRs over overlapping rewrites. Reference the earlier PRs and explain how your change extends or integrates them.
